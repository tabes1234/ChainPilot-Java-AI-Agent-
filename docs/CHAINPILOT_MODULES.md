> 本文件是开发阶段的模块梳理，保留了历史 Nuxt 前端和早期评测口径。当前前端入口、
> 启动方式、模型门禁和最新验证状态以 [README](../README.md)、

ChainPilot is built by extending the Spring AI Alibaba DataAgent source. The existing application remains the host platform; supply-chain capabilities are isolated in the backend's supplychain package.

## Kept

- data-agent-management: Spring Boot management API, model configuration, data-source connectors, chat/session APIs, MCP server, and security.
- Existing workflow, service/graph, and NL2SQL pipeline: Spring AI Alibaba StateGraph orchestration, planning, execution validation, retry routing, and report generation.
- Existing vector retrieval and knowledge management: Spring AI vector stores, document ingestion, metadata filtering, and retrieval services.
- data-agent-frontend-nuxt: existing administration and agent UI, with a ChainPilot supply-chain analysis page and navigation entry; original admin and agent pages remain available.
- Docker and database initialization assets.

## Changed

- Maven display and artifact names now use ChainPilot.
- Application name, README, and Docker artifact path use ChainPilot.
- No existing DataAgent controller, workflow, persistence, or front-end feature was removed.

- supplychain/model and repository: deterministic order, inventory, supplier-risk, task-status, paged task-history, report, citation, and structured execution-event records.
- supplychain/service: risk scoring, query tools, best-effort execution-event recording at node/tool/model boundaries, and the ChainPilot analysis flow.
- supplychain/controller: query APIs plus analysis submission, filtered/paged task history, task-state lookup, report retrieval, and per-task execution-event retrieval.
- supplychain disposal slice: rule-based recommendations, deterministic what-if simulation (inventory replenishment and supplier delay), persisted plans/simulations with status history, SOP citations, and model-or-fallback explanations.
- supplychain/controller: `/api/supply-chain/disposal-recommendations`, `/disposal-simulations`, and `/disposal-plans` APIs with validation, pagination, and 400/404/409 error mapping.
- supplychain comparison slice: 2–5 any-scenario candidates sharing one baseline snapshot and SHA-256 fingerprint, deterministic lexicographic Java ranking with tie-break and incomparable outcomes, persisted comparisons/candidate simulations/rankings/recommendations, candidate save-as-copied-plan, candidate-to-plan linking, and paged comparison history.
- supplychain/controller: `/api/supply-chain/disposal-scenario-comparisons` create/history/detail, `/candidates/{candidateId}/disposal-plans`, and `/candidates/{candidateId}/plan` APIs; invalid candidate counts, duplicate parameters, mixed scope/baseline, repeated saves, and mismatched plan links return 400/404/409 as appropriate.
- resources/knowledge/supply-chain: three versioned fulfillment, inventory, and supplier-risk SOP documents.

- comparison tests for 2–5 boundaries, distinct quantities, shared baseline, ties, incomparable inputs, ranking/reason consistency, persistence, repeated saves/links, HTTP history/detail/errors, and a local fake-model tool call proving the model explains the persisted comparison rather than recomputing it.
- data-agent-frontend-nuxt disposal workspace embedded in the supply-chain page: recommendations, scenario form/results, before/after comparison, plan save/history/detail, simulation history, status actions, sandbox execution eligibility/start/detail/history, repeat-click guard, retries, and explicit raw/rule/model/sandbox/real-operation labels; the same workspace includes a 2–5 candidate comparison editor, deterministic result/ranking/recommendation display, comparison history, save-as-plan/link actions, and handoff to the existing sandbox flow, with unit tests covering services, composable state, idempotency, and failures.
- natural-language decision workspace embedded in the same page: DECISION task submission and polling, grounded summary with `narrativeSource`, clarification prompts, tool-call/evidence display, candidate rankings and simulation metrics, recommendation reasons, pending proposals with hash-bound confirm/cancel/edit, linked plan/execution records, history status filters and pagination, event-timeline handoff, anti-duplicate submit guards, and explicit distinctions between raw data, Java rule results, simulations/rankings, model explanation, rule fallback, proposals, and confirmed execution results.
- supplychain decision slice: deterministic `SupplyChainDecisionIntentParser` over a `DECISION` task type, per-intent read-only tool dispatch, evidence-grounded narrative with `MODEL_GROUNDED`/`DETERMINISTIC`/`DETERMINISTIC_FALLBACK`, clarification instead of unrelated defaults, and deterministic creation of proposals for save/link/select/start-sandbox operations.
- supplychain proposal boundary: `chainpilot_action_proposal` persists action type, target, parameters, evidence, SHA-256 content hash, 30-minute expiry, status and result; identical pending proposals per task are deduplicated, confirmation atomically claims `PENDING → EXECUTING`, revalidates task/target/plan/eligibility state, delegates to the existing plan or sandbox service, and replays idempotently. The model has no write tool, so no natural-language request can directly save, select, link, or start a sandbox execution.
- decision tests: intent parsing (scope, candidate count/uniqueness, mixed parameters, explicit IDs), service behavior (grounding, clarification, model failure, tool failure, proposal creation), proposal state/hash/expiry/duplicate-confirmation transitions, HTTP end-to-end with a local fake model and real Java tools, frontend service/composable/duplicate-guard tests, and MySQL persistence/cascade of decision results and proposals.
- risk explainability and traceability: `RiskEvidence` now carries structured observed/expected values, rule text, score contribution, source and availability for delay, inventory, supplier and overdue checks; `OrderRiskAssessment` also exposes `dataGaps` when inventory or supplier snapshots are missing and does not invent a shortage. The analysis report and baseline order table show this evidence, while decision/disposal views expose recommendation business basis/prerequisites/assumptions, proposal timestamps, plan task/status timestamps, sandbox execution mode/timestamps and the existing task event timeline. No database schema change was needed; the extra fields live in the existing JSON payloads.
- model narrative boundary: the report model returns a structured JSON explanation (`overview`, per-order reasons with evidence IDs, impacts, recommendations, uncertainties). `RiskNarrativeValidator` rejects unknown evidence IDs, ungrounded numbers, out-of-scope recommendations, execution claims, malformed JSON and omitted data gaps; rejected output falls back to the Java summary. `RiskAnalysisReport.narrativeSource` marks `MODEL_VERIFIED`, `MODEL_LEGACY_UNVERIFIED` (old persisted free-text reports) or `DETERMINISTIC_FALLBACK`, and the workflow validates that missing inventory/suppliers have explicit evidence-backed data gaps instead of failing the task.
- scenario simulation boundary: the disposal workspace exposes a read-only baseline (`GET /api/supply-chain/disposal-simulations/baseline`) with assessments, inventory, suppliers, rule version and data gaps. Deterministic simulations reuse the analysis risk rule and add `ruleVersion`, `simulationStatus=SIMULATED`, top-level data gaps, and per-order evidence changes/remaining gaps. Comparisons share one fingerprinted baseline, rank only Java-computed metrics, and persist candidate simulations; missing data is shown but never replaced with invented values.
- agent observability (`/agent-observability`): a read-only 200-task window over existing `chainpilot_analysis_task`/`chainpilot_task_event` records exposes summary, paged run filters (`status`, `mode`, `narrativeSource`, `fallback`, `failureType`, `query`) and per-task diagnostics. Detail reuses persisted events only (no duplicated execution log) and returns timeline, tool/model result summaries, fallback reasons, narrative source, report facts, proposal/plan links and evaluation task references. Diagnostics are deterministic rules; model identity/Token/cost and tool input bodies are not available in historical events and are explicitly marked unavailable. APIs: `/api/supply-chain/observability/{summary,runs,runs/{taskId}}`.
- agent evaluation center (`/agent-evaluation`): a versioned 20-case catalogue (14 deterministic offline cases plus 6 real-workflow cases), persisted runs and per-case results with `case_version`/`task_mode`, explicit-start AGENT runs requiring `confirmAgentRun=true` plus a process-local single-run guard and 20-minute timeout, per-case assertions and failure reasons, real task-event/report links, per-case history, and mode-separated metrics computed only from complete terminal runs (pass/fail/undetermined rates, case and run average/P95 with a five-sample guard, scenario results, top failure reasons, lexical HitRate@3/MRR or null). OFFLINE runs call the real deterministic services without models or business writes; AGENT runs may incur model/embedding cost and never execute the sandbox. Interrupted/timed-out runs are closed as FAILED with running cases UNDETERMINED. `GET /api/agent-evaluation/comparisons` compares two persisted runs only when mode, case-set version, case ids and assertion ids agree, returning new/fixed/persistent failures and assertion-level diffs. Single-case rerun always creates a new run and preserves history. DDL and additive upgrades: `src/main/resources/sql/agent-evaluation.sql`; MySQL 8 coverage: `EvaluationMySqlPersistenceIT`; docs: `docs/DEMO_GUIDE.md`.

## Workflow direction

The supply-chain analysis path uses a separate Spring AI Alibaba StateGraph, keeping the existing NL2SQL graph intact. It plans, queries orders/inventory/suppliers, validates risk evidence, retries one time on invalid evidence, and produces a report. Tasks can be submitted to a bounded background executor and polled. Task states and completed reports are persisted in the configured SQL database, and task history is exposed with database-level status filtering and `updated_at DESC, task_id DESC` pagination; the response body stays an array for the existing page while `X-Total-Count`/`X-Page`/`X-Page-Size`/`X-Total-Pages` carry paging metadata. `limit` remains a backward-compatible page-size alias, with `pageSize` taking precedence. Terminal task retention is capped at 24 hours and 1,000 records, and a restart marks unfinished jobs as failed instead of resuming them. Tool methods use Spring AI's existing @Tool mechanism and write start/success/failure events. The model-facing set is `findAtRiskOrders`, `findInventory`, `findSuppliers`, `findDisposalRecommendations`, `simulateInventoryReplenishment`, `simulateSupplierDelay`, `compareDisposalScenarios`, `compareSupplierDelayScenarios`, `findScenarioComparison`, `findDisposalPlan`, `checkSandboxExecutionEligibility`, `findSandboxExecution`, and `findSandboxExecutions`; `startSandboxExecution` is intentionally not exposed. These tools reuse the same deterministic services and evidence recorder, and sandbox tools cannot write real inventory, orders, suppliers, or ERP data. Disposal plans store recommendations, simulation snapshots, citations, explanation source, and status; plans can reference at most one simulation, and simulations can be attached to at most one plan. Comparisons are stored separately with candidate rows and copied simulations, so saving a candidate as a plan preserves the comparison relationship without relaxing that constraint. The what-if engine copies orders and inventory, reruns the existing risk assessment, returns baseline/simulated/delta/affected orders, and never writes to real business data. The comparison engine captures one baseline for all candidates, reuses that same simulation engine, and ranks only existing metrics; the model receives the persisted comparison result and may explain it but cannot produce candidates, metrics, ranks, or evidence on its own. Sandbox execution follows a `RUNNING → SUCCEEDED | FAILED` state machine with five persisted, code-executed steps; a plan-row lock plus unique `(disposal_plan_id, idempotency_key)` makes replays return the original record and blocks conflicting starts, while a running or successful execution prevents a second rehearsal. Failures keep completed/failed steps and can be retried with a new key. Before/after data fingerprints prove real records were not mutated; the record links plan, selected recommendation, source simulation, evidence, and generated draft. Only local single-database transaction semantics are claimed. Node execution, tool invocation, model completion/failure, and deterministic fallbacks also create per-task events with a monotonic sequence; `GET /api/supply-chain/analysis/tasks/{taskId}/events` returns only that task's trail. Event persistence is best-effort: a failure is logged with diagnostic context but never changes task status, reports, or fallback behavior. Events store safe summaries and error class names only; prompts, model output, tool arguments, credentials, and exception messages are not persisted. SOP retrieval reuses the configured Spring AI VectorStore when an embedding model is available, and falls back to local keyword retrieval otherwise; both paths return the source ID. Natural-language decision tasks reuse the same async task table, event trail, model factory, and Java tool services. A deterministic parser selects the intent and arguments; Java invokes the read-only tools, and only those computed results are passed to the narrative model, which has no tool or write access. Ambiguous scope returns a clarification without spending a model call. Write-like requests create hash-bound proposals instead of executing; confirmation revalidates task, target, plan, and sandbox eligibility state before calling the existing plan or sandbox service. Events record intent, tool, validation, model, fallback, proposal, confirmation, and execution stages with safe summaries only. The existing dynamic model registry remains the sole place to configure model credentials; no API key is stored in source.
